#### Blocking Issue 1 — `load_prices`: no file-open guard (`csv_loader.cpp:49`)

**What was wrong:** `std::ifstream file(filepath)` constructs the stream object and attempts to open the file. If the path is wrong, the stream enters a fail state at construction — not during the loop. The first `std::getline(file, line)` (header skip) silently does nothing. The while loop sees a false stream immediately and never runs. Function returns an empty `std::vector<double>`. The caller has no way to distinguish "file not found" from "file exists but is empty."

**User's initial answer (before opening code):** "std::ifstream returns falsey in the while loop — causes load_prices to return empty; should have an assert or guard." Direction correct; key nuance missed: the stream fails at construction, not in the loop.

**User's initial fix attempt:**
```cpp
if (!file.is_open()) {
    std::cerr << "Failed to open file" << "\n";
}
```
Missing a `return` or crash — execution falls through silently. Identified and corrected after one coaching step.

**Hint given:** "your snippet prints the error and then falls through — execution continues past the if." Reason given: functions must either return or crash to stop — printing alone changes nothing about program state.

**Final fix applied:**
```cpp
std::ifstream file(filepath);
if (!file.is_open()) {
    std::cerr << "Failed to open file: " << filepath << "\n";
    assert(false);
}
std::string line;
std::getline(file, line);  // header skip — now only reached if file opened
```

Key point reinforced: guard must come before any use of the stream. `assert(false)` crashes at the right location with file + line info from the assert macro. `filepath` in the message makes the error actionable.

#### Blocking Issue 2 — integer index arithmetic in `historical_VaR` and `monte_carlo_VaR` (`var_model.cpp:15-16`, `42-43`)

**What was wrong:**
```cpp
double hist_VaR_95 = log_return_cpy[(log_return_cpy.size() * 5/100) - 1];
```
`size()` returns `size_t` (unsigned). If `size() * 5 / 100 == 0` (happens when N < 20), the subtraction `0 - 1` wraps to `SIZE_MAX` in unsigned arithmetic — out-of-bounds index access. Works correctly for N=500 (the current dataset) but is a latent bug for any smaller input.

**User's proposed fix:** `static_cast<unsigned int>` on the final index value. Incorrect — the wrap happens during the arithmetic intermediate, before the cast. Casting the already-wrapped value to `unsigned int` still gives a huge number.

**Hint given:** "the wrap happens during the arithmetic, before the cast — you need to get into signed space first so `0 - 1` evaluates to `-1`, not `SIZE_MAX`." Reason: signed integer arithmetic does not wrap; `-1` is just `-1`.

**Final fix applied (both functions):**
```cpp
int n = static_cast<int>(log_return_cpy.size());
int idx_95 = (n * 5 / 100) - 1;
int idx_99 = (n * 1 / 100) - 1;
assert(idx_95 >= 0 && idx_99 >= 0 && "Not enough returns for VaR calculation");
```
`monte_carlo_VaR` used `int n_mc` to avoid naming collision with the `NormalSampler n` object in the same function.

### 3. Empirical Exceedance Frequency — concept introduction

**Context:** The W8 curriculum acceptance test requires an out-of-sample exceedance frequency check. This was introduced conceptually to set up Day 4.

**Definition (taught):** An exceedance is one day where the actual loss was worse than the VaR threshold. Empirical exceedance frequency = (number of exceedance days) / (total out-of-sample days). For a well-calibrated 95% VaR, this should be close to 5%.

**Why out-of-sample matters (taught):** Historical VaR at 95% is computed by sorting returns and taking the 25th worst out of 500. By construction, exactly 24/500 = 4.8% of that same dataset will exceed it. Testing on calibration data is circular — the test will always "pass" regardless of model quality. Out-of-sample (e.g., calibrate on years 1–2, test on year 3) tests whether the model generalises.

**Fat tails connection (user-initiated):** If parametric VaR understates tail risk, actual exceedance rate will be above 5%. User correctly identified fat tails as the reason — the model assumes a thin-tailed normal distribution; real returns have more extreme events.
