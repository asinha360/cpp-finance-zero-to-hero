## Concepts covered

**Time value of money.** A dollar today is worth more than a dollar in the future because money held today can earn a return. If you invest PV at rate r for n periods, you receive FV = PV × (1+r)^n. Solving for PV: PV = FV / (1+r)^n.

**Why `double` not `float`.** Floating-point numbers have rounding errors. When you compound a rounding error repeatedly over n periods, errors accumulate multiplicatively. `double` has roughly twice the precision of `float` (64-bit vs 32-bit), so errors stay smaller for the same number of compounding steps. This was reasoned correctly and unaided.

**`-Wall` compiler flag.** Turns on the compiler's warning system. Warnings are not errors — the code still compiles, but the compiler flags suspicious patterns (e.g., reading an uninitialised variable, accidental assignment in a condition). Without `-Wall`, these pass silently and the program may misbehave. Understood after one hint.

**Undefined behavior (UB) — first exposure.** Reading an uninitialised variable is UB. The compiler does not refuse to compile, and the program does not necessarily crash. The CPU reads whatever bytes happen to be at that stack address from a previous function call. This was the first introduction; mechanism needed scaffolding.

## Spec locked

```
Inputs:  FV: double
         r:  double   — guard: reject r == -1.0 (division by zero in (1+r)^n)
         n:  int
Output:  PV: double, printed to 2 decimal places
```

**Edge case reasoning:**
- `r = -1.0`: (1+r) = 0, denominator is 0, formula undefined. Must reject.
- `n < 0`: Mathematically defined (raises to a negative power), result is unusual but not a crash. Document, do not reject.
- `n = 0`: (1+r)^0 = 1, so PV = FV. Correct and safe.
- Large `n`: (1+r)^n → ∞, so PV → 0. Safe numerically.
- Negative `FV`: Mathematically valid. No guard needed.
