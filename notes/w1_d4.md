## Summary

## Blocking issues fixed

**Silent `return 1` on `r == -1.0` guard.**
Original code returned 1 silently with no message to the user. The user had no way of knowing why the program exited.
Fix: emit a `std::cerr` message explaining the rejection before returning.

This introduced the `std::cerr` vs `std::cout` distinction:
- Both write text to the terminal by default.
- They are separate OS-level streams. Callers (scripts, pipelines) can redirect them independently: `2>errors.txt` captures only `std::cerr`.
- Convention: `std::cerr` for errors and diagnostics; `std::cout` for program output.
- Understanding: "separate OS streams, not just error-vs-success labeling" — correct.

## Non-blocking suggestions logged

1. **Floating-point equality pattern:** Comparing `r == -1.0` is technically fragile for floating-point (two doubles that should be equal may differ by a tiny rounding error). For this program, where `r` comes from a user-typed literal, it is safe. The general pattern of using a tolerance band (`std::abs(r - (-1.0)) < 1e-9`) was introduced as a concept to apply in W4.

2. **`n < 0` silent behavior:** The program accepts negative `n` and computes a result that makes mathematical sense but is unusual. No crash, but behavior should be documented. Logged for awareness; not changed (documented edge case behavior, not a bug).
