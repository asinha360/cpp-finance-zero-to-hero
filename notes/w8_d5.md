### 1. Opening retrieval — parametric + historical VaR exceedance divergence

**Background for future-Claude:** VaR (Value at Risk) is a loss threshold such that actual portfolio losses exceed it only X% of the time. 95% VaR means "losses exceed this level only 5% of days." Exceedance frequency is the fraction of out-of-sample days where the actual log return was worse (more negative) than the VaR threshold. Out-of-sample means data not used during calibration — testing on calibration data is circular because historical VaR by construction produces exactly 5% exceedances on its own data.

Our data: 350-return calibration window, ~150-return out-of-sample window. Parametric VaR produced 6.2% exceedance (expected 5%); historical produced 4.6% (expected 5%).

- **Objective:** State the distinct reason for each method's deviation from the 5% target.
- **Solo attempt:** yes

**Parametric side — score: 1/2**
- User said: fat tails; normal distribution underestimates left-tail frequency; "a lot of those exceedance events are closer to the mean."
- Direction correct. Mechanism partially right. Muddled phrase: "events closer to the mean." The error lives in the threshold placement, not event distribution: the normal distribution underestimates how far the left tail extends, so the 5th percentile it computes is too close to zero (not negative enough). More actual returns fall past a too-shallow threshold.
- Hint given (rung 1): "The threshold is set too shallow — not that events cluster near the mean. Where does the error live?" — Why this direction: parametric VaR error is entirely about threshold placement; reframing from events to threshold prevents students from conflating two separate ideas.

**Historical side — score: 0/2 (3 coaching passes to clean statement)**
- User said: "often can overstate exceedance frequency… can overestimate exceedance in an out-of-sample testing dataset due to overfitting."
- Direction wrong. 4.6% < 5% is undershooting, not overstating.
- Coaching step 1: "You said 'overstate' — but our number is 4.6%. Is 4.6% an overstatement or understatement of 5%?" — Why this direction: anchoring to the concrete number forces the student to reconcile their claimed direction before reasoning about mechanism. Without this, mechanism reasoning proceeds in the wrong direction.
- User corrected to understatement.
- User then said: "anchored too closely to the extremes in its calibration window." Direction now correct; mechanism incomplete — no explanation of WHY this produces undershooting.
- Coaching step 2: "Why does anchoring to calibration extremes cause undershooting specifically? What would have to be true about the calibration window vs. out-of-sample window?" — Why this direction: anchoring could cause over or undershooting depending on relative volatility. The comparison between windows is the missing causal link.
- User said: "The calibration window must have a lower percentage of the lower lows." Direction reversed again — fewer extremes → less negative threshold → more exceedances → overshoot.
- Coaching step 3 (rung 2): "If calibration had many big down days, would the 5th percentile threshold end up more or less negative? And a very-negative threshold applied to a calmer out-of-sample period — more or fewer exceedances?" — Why this direction: breaking the causal chain into two sequential directional questions forces the student to reason through each step rather than guess the conclusion.
- Final clean statement: "Historical VaR sorts returns within a calibration window and sets 5th percentile as threshold; if this window contains many big down days relative to an out-of-sample period, our threshold would be more negative, and when applied to a calmer out-of-sample period, would produce fewer exceedances than expected." ✓

### 3. Main exercise — assert-based acceptance checks

**Acceptance criteria (from TASKS.md):**
1. 99% VaR more negative than 95% VaR (in magnitude) — for all three methods.
2. All exceedance rates within [0%, 15%].

**3a. Magnitude ordering**

- Solo attempt: `assert(hvar95 > hvar99)` for historical ✓. Also wrote `assert(hist_ex_freq_95 > hist_ex_freq_99)` — not one of the criteria (comparing two rates, not bounding each).
- Coaching: "The criterion says exceedance rates in [0%, 15%] — it's a bound on each rate individually, not a comparison between them." Criterion must be read precisely before translating to code.
- Parametric and MC magnitude asserts were missing; user prompted to write all three.
- Correct form: `assert(hvar95 > hvar99)` — both values are negative; hvar95 (e.g., −0.026) is less negative than hvar99 (e.g., −0.035), so `>` is correct.

**3b. Exceedance bound — two bugs caught**

Solo attempt: `assert(0 < hist_ex_freq_95 < 15);`

Bug 1 — chained comparison. In C++, `0 < x < 15` evaluates left-to-right: `(0 < x)` → `true` → `1`, then `1 < 15` → always `true`. This assert would never fire even if the value is 200.
- Hint: "C++ evaluates left-to-right: `(0 < hist_ex_freq_95)` produces `true` (which is `1`), then `1 < 15` is always true. How do you combine two conditions?" — Why this direction: the user must understand why the original always evaluates true before the fix (`&&`) makes sense; otherwise it's mechanical substitution without understanding.

Bug 2 — units. `exceedance_frequency` returns a ratio (e.g., 0.046 for 4.6%), not a percentage (4.6). Bound should be `0.15`, not `15`.

After corrections: `assert(hist_ex_freq_95 >= 0.0 && hist_ex_freq_95 < 0.15)` ✓
- User correctly chose `>= 0.0` (not `> 0.0`): "it can legally be 0." ✓

**3c. Final assert block (all 9, placed by user)**

```cpp
assert(hvar95 > hvar99);
assert(hist_ex_freq_95 >= 0.0 && hist_ex_freq_95 < 0.15);
assert(hist_ex_freq_99 >= 0.0 && hist_ex_freq_99 < 0.15);
assert(pvar95 > pvar99);
assert(para_ex_freq_95 >= 0.0 && para_ex_freq_95 < 0.15);
assert(para_ex_freq_99 >= 0.0 && para_ex_freq_99 < 0.15);
assert(mcvar95 > mcvar99);
assert(mc_ex_freq_95 >= 0.0 && mc_ex_freq_95 < 0.15);
assert(mc_ex_freq_99 >= 0.0 && mc_ex_freq_99 < 0.15);
```

Placement: after each method's variables are computed, before that method's print block. Rationale: assert fires before printing results that haven't been validated.
