## Summary

Code review of `price_series.cpp`. Two blocking issues found and fixed. Two non-blocking suggestions applied. All fixes verified: output still matches Python reference to 4 d.p. after changes.

## Blocking issues fixed

**1. Guard threshold wrong: `<= 1` changed to `<= 0`.**

Original guard: `if (prices.size() <= 1) { return error; }`

Problem: the mean is mathematically defined for n=1 (it's the single value itself). Guarding at n≤1 incorrectly rejected valid single-element input.

Fix: `if (prices.size() <= 0)` — only reject empty vector. For n=1, mean is valid; variance is undefined (return NaN or document), but mean must be allowed.

Lesson: guard conditions must match the actual mathematical domain of the function, not a conservative approximation of it.

**2. `price_series` global variable not marked `const`.**

The global price series is never modified after initialisation. Marking it `const` communicates this invariant and prevents accidental modification. Fix: add `const` to the global declaration.

## Non-blocking improvements applied

**`returns_vector()` parameter change.**

Original: function read from the global `price_series` directly.

Fix: changed to `returns_vector(const std::vector<double>& prices)` — takes the input as a const-ref parameter rather than accessing a global. This is the first time this pattern was applied in a code review fix (first coded application of const-ref, after being introduced in W2 and scaffolded in W3).

Benefits: function is now testable in isolation, and does not depend on the global existing.

**Parameter rename: `mean` → `mean_val` in `sample_variance()` and `standard_deviation()`.**

The parameter was named `mean`, which shadows the function `mean()` defined earlier in the same file. When inside `sample_variance()`, the name `mean` resolved to the parameter, not the function. This works correctly but is confusing and could cause bugs if the shadowing were unintentional. Renamed to `mean_val` to remove the ambiguity.

Lesson: avoid naming a variable the same as a function in the same scope. The compiler does not error on this — it silently prefers the nearest binding.
