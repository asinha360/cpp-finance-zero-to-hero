**Bug 2 caught — division by zero on empty vector:**
- `double mean = price_sum / price_vec.size()` where `price_vec.size()` returns `size_t` (unsigned integer). If all rows are malformed, `size()` = 0; `0.0 / 0.0` = `NaN` (IEEE 754 "Not a Number" — a bit pattern meaning the result is mathematically undefined; prints as `nan`; propagates silently through further arithmetic).
- Student initially said "undefined behaviour." Corrected: *integer* division by zero is undefined behaviour (CPU instruction traps); *floating-point* division by zero on IEEE 754 machines (universally used in practice) produces `NaN` or `Inf` — a defined but wrong result. The practical problem (silent wrong output) is the same; the mechanism differs.
- Hint given: "What is `price_vec.size()` if every row is malformed? What does dividing by that produce for a `double`?" Why-this-direction: student needed to identify both the input value (0) and the C++ semantics of double/0 before choosing a fix.
- Student proposed two solutions:
  - `assert(price_vec.empty())` — two problems: (1) condition inverted — asserts when vector IS empty, which fires in the normal non-empty case; (2) wrong tool — `assert` is for internal invariants that cannot happen if code is correct; it is compiled out with `-DNDEBUG` in release builds; user-facing error conditions (malformed input) need a real runtime `if`.
  - `if (!price_vec.empty()) { ... } else { std::cerr << ...; return 1; }` — correct.
- Fix applied: if/else guard adopted.

**Bug 3 introduced and caught — load-bearing `continue` removed:**
- While cleaning up, student removed the `continue` from the `if (pos == std::string::npos)` npos guard (not what I asked). I had noted the `continue` inside the catch block was redundant — student removed the wrong one.
- Result: `BADROW` printed twice in output.
- Path: npos guard prints "malformed row" → no `continue` → falls through to `line.substr(pos + 1)` where `pos = npos`; `npos + 1` wraps to 0 (unsigned overflow — see W7D1 notes); `substr(0)` returns whole line; `stod("BADROW")` throws `std::invalid_argument`; catch fires; second "malformed row" prints.
- Student correctly traced this: "if(npos) block & catch both print malformed row — removed continue for the if so execution reaches second one." Score on tracing: 2/2 unaided.
- Hint to reach structural understanding: "Look at where each `continue` sits relative to the rest of the loop body. After the catch block closes, what is the next statement still inside the loop?" Why-this-direction: the distinction is positional — a `continue` only matters if there is code below it inside the loop body; the student needed to locate both `continue` statements relative to the end of the loop.
- Student answered: "Its before the mean calculation." Wrong — mean calculation is outside the loop entirely.
- Full explanation given: a `continue` skips code that is (a) below it AND (b) still inside the loop body. The npos `continue` has `substr` calls and the `try` block below it — load-bearing. The catch `continue` is the last statement in the loop body; nothing after it inside the loop — redundant. The structural rule: `continue` at the very end of a loop body skips nothing; the loop iterates anyway.
- Score on structural question: **0/2** — concept explained but not independently retrieved. Carry-forward to Day 3.
- Fix: `continue` restored to npos guard, removed from catch.

Final state: zero warnings, single BADROW, mean 477.832.
