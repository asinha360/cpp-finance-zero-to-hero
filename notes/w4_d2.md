## Part 1 — Retrieval practice

### UB mechanism (spaced retest from W1)

**Question:** When a variable is declared but not initialised in C++, the compiler doesn't refuse and the program doesn't crash. Why? What is happening at the machine level?

**Answer given:** The compiler reads the last written data stored at the memory address where the variable was initialised, and could produce garbage results, optimise the variable away entirely, or produce plausible yet misleading results. The program does not crash because C++ is an execution-focused language that assumes complete user accuracy.

**Assessment: 2.5/3.**
- Three outcomes (garbage, optimised away, plausible-but-wrong) ✓
- Machine-level mechanism (leftover stack bytes from prior function call) ✓
- WHY no crash: "assumes user accuracy" is philosophically right but mechanistically incomplete. The precise reason: reading a stack address is a valid CPU instruction. The CPU fetches whatever is at that address. C++ does not insert a runtime check ("was this written before?") because that check would cost CPU cycles — and C++ refuses to pay for things you didn't ask for. This principle is the **zero-overhead principle**.

## Part 2 — Conceptual deepening

### The BS equation — two-term structure sharpened

```
C = S·N(d1) − K·e^(−rT)·N(d2)
```

- **N(d2):** Risk-neutral probability that S_T > K (option finishes in the money). Weights the K payment.
- **N(d1):** The delta — ∂C/∂S. How much the call price moves for a $1 move in S. Not the same probability measure as N(d2). Weights the S receipt. The difference between d1 and d2 is σ√T, reflecting different probability measures.

**d1 vs d2 distinction — check question result:**
Student said the σ²/2 term is added in d1 and subtracted in d2. Mechanical difference correct ✓. Attributed N(d1) to weighting the K payment — wrong (that is N(d2)). Corrected after one prompt.

### Macro applications (introduced — no prior context)

- **Options pricing:** Banks and desks use BS to quote call/put prices.
- **Implied volatility:** BS run backwards — observe market price, solve for σ. Implied vol is the market's embedded expectation of future uncertainty.
- **Delta hedging:** N(d1) tells a market maker how many shares to hold to cancel small moves in S. Rebalance continuously to stay neutral.
- **Where BS breaks:** Assumes constant vol and continuous price moves with no jumps. Real markets violate both. This explains the "vol smile/skew" — implied vol varies with strike and expiry.

## Part 3 — Implementation planning

### Implementation outline (built incrementally via coaching)

The outline was not given — it was constructed through questions, with errors caught and corrected at each step.

**Key errors caught during planning:**
1. normal_cdf described as returning N(d1) and N(d2) — a function has one return value; it returns a single probability for whatever x is passed in.
2. The + sign in the BS formula instead of − (critical error caught before coding).
3. delta and vega return labels swapped.
4. d1 listed as the only intermediate step — four steps needed: d1, d2, N(d1), N(d2).

**Final outline:**
```
1. normal_pdf(x)               — (1/√2π)·e^(−x²/2)
2. normal_cdf(x)               — 0.5·(1 + erf(x/√2)), a probability in [0,1]
3. blackScholesCall(S,K,r,σ,T) — d1 → d2 → N(d1) → N(d2) → S·N(d1)−K·e^(−rT)·N(d2)
4. delta(S,K,r,σ,T)            — normal_cdf(d1)
5. vega(S,K,r,σ,T)             — S·√T·normal_pdf(d1)
6. main()                      — calls all three, prints results, verifies T=1 test
```

### std::erf relationship to normal CDF

```
Φ(x) = 0.5·(1 + erf(x/√2))
```

`erf(x)` lives on (−1, 1); the normal CDF lives on (0, 1). The x/√2 transformation and the 0.5 scaling convert between them. Requires `#include <cmath>`.

### normal_pdf derivation

Differentiation direction: PDF = d/dx [CDF]. Differentiating Φ(x) = 0.5·(1+erf(x/√2)) via chain rule gives:

```
φ(x) = (1/√2π)·e^(−x²/2)
```

Student attempted to differentiate erf(x) directly instead of Φ(x) — caught. Chain rule through x/√2 was needed. Result provided after coaching attempt failed on the chain rule step.

### delta derivation

**Question:** What is ∂C/∂S from the formula C = S·N(d1) − K·e^(−rT)·N(d2)?

**First answer:** N(d1) − K·e^(−rT)·N(d2) — student differentiated both terms.

**Coaching question:** Does the second term contain S anywhere? Answer: No. Fix: ∂/∂S of a term with no S is 0.

**Corrected answer:** delta = N(d1). Already computed inside the pricer; costs nothing additional.

## Part 4 — Code written

### Functions implemented

```cpp
double normal_pdf(double x)

double blackScholesPut(double S, double K, double r, double sigma, double T)

double vega(double S, double K, double r, double sigma, double T)

```

### Two bugs found and fixed

**Bug 1 — r not multiplied by T in d1 numerator.**

Original:
```cpp
(r + ((sigma * sigma) / 2.0) * T)
```

This computes `r + (σ²/2)·T`. The correct numerator is `(r + σ²/2)·T` — both r and σ²/2 must be multiplied by T.

Fixed:
```cpp
(r + ((sigma * sigma) / 2.0)) * T
```

**Bug 2 — operator precedence in denominator.**

Original:
```cpp
/ sigma * std::sqrt(T)
```

Left-to-right evaluation: `(numerator / sigma) * sqrt(T)` — multiplies sqrt(T) into the result instead of dividing by it. Correct denominator is `sigma * sqrt(T)`.

Fixed:
```cpp
/ (sigma * std::sqrt(T))
```

**Why both bugs were invisible at T=1:**
- Bug 1: `r = r·1 = r` ✓
- Bug 2: `sqrt(1) = 1`, so `/ sigma * 1 = / sigma` ✓

The acceptance test at T=1 passed with the buggy code. Only testing at T=0.5 revealed the errors. This is the "plausible yet misleading result" from the UB discussion — applied now to a math formula bug.

**T=0.5 results after fix:** Call Price: 6.89 ✓ (coach gave wrong reference of 5.57 — acknowledged and corrected; 6.89 is the correct value).

### Edge case guards

Guards added for sigma=0 and T=0 (division by zero in the d1 denominator). Implemented inside `blackScholesCall` and `blackScholesPut`, and also in `main()` before the function calls.

Structural note: guards in `main()` only protect the interactive path. If the functions are called directly (e.g., from a unit test) with sigma=0, they will still divide by zero. For a standalone pricer, acceptable. For a library function, guards should live inside the function exclusively.

### Put-call parity

**Derivation from payoff reasoning:**

| Scenario | Long call | Short put | Net |
|----------|-----------|-----------|-----|
| S_T > K | S_T − K | 0 | S_T − K |
| S_T ≤ K | 0 | −(K − S_T) | S_T − K |

Net payoff = S_T − K in both cases. Same payoff as owning the stock and borrowing K·e^(-rT) today. No-arbitrage → prices must be equal:

```
C − P = S − K·e^(−rT)
```

**Numeric check:** S=100, K=100, r=0.05, T=1 → `100 − 100·e^(−0.05)` = 4.88. Student computed 4.87 (rounding). Correct ✓.

**Put pricer implemented:**
```
P = K·e^(−rT)·N(−d2) − S·N(−d1)
```

Same d1 and d2 as the call; arguments to normal_cdf negated. Code correct.

### Assert-based unit tests

```cpp
#include <cassert>

void runTests() {
    double S = 100, K = 100, r = 0.05, sigma = 0.2, T = 1.0;
    double C = blackScholesCall(S, K, r, sigma, T);
    assert(std::abs(C - 10.45) < 0.01);           // price test

    double P = blackScholesPut(S, K, r, sigma, T);
    assert(std::abs(C - P - (S - K * std::exp(-r * T))) < 1e-10);  // parity test
}
```

Both asserts pass silently. `runTests()` called at the top of `main()` before any user input.

**Error in first draft of runTests:** Parameters S, K, r, T were passed in from main but C and P were hardcoded with literal values — mismatch between parameter values and hardcoded values. Fixed by removing parameters and defining S, K, r, sigma, T as local variables inside `runTests`.
