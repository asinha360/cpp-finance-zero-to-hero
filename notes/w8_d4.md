### 3. Main exercise — implement `exceedance_frequency`

#### 3a. Identify the exceedance condition

- **Objective:** State the condition for one exceedance: return `r` vs threshold `var_threshold`.
- **Solo attempt:** yes — wrote `r > var_threshold` (wrong direction).
- **Hint given (rung 1, ~5 min):** "VaR is a negative number — think about what -0.0256 means. If the actual return on a given day is -0.04, does that count as an exceedance? Which side of -0.0256 is -0.04?" — **Why this direction:** VaR is a loss threshold on the negative side of the number line. A worse loss is more negative (further left), not more positive. Working through a concrete example forces the direction rather than guessing a symbol.
- **Accepted after hint:** `r < var_threshold` ✓

#### 3b. Denominator type for frequency calculation

- **Objective:** Identify why `static_cast<int>(size())` in the denominator is wrong.
- **Solo attempt:** "produces an unsigned type — which could cause arithmetic overflow?" (near miss — wrong root cause).
- **Hint given (rung 1):** "What does C++ produce for `3 / 60` as integer division?" — **Why this direction:** the actual danger is silent truncation to zero, not overflow. Integer division `count / total` with both as `int` gives 0 whenever count < total. Naming the concrete failure mode prevents similar bugs across all frequency/ratio calculations.
- **After explanation:** understood; applied `static_cast<double>(count) / total` correctly ✓

#### 3c. Write the full function

- **Solo attempt:** wrote correct body; used `double count = 0` as counter type (non-standard but functionally correct).

For 500 returns that's 500 doubles copied and immediately thrown away." — **Why this direction:** const-ref = no copy + read-only promise, a pattern applied since W2. Framing the cost as concrete heap work (not just "convention") makes it memorable.

#### 4b. Iterator arithmetic

### 5. Print formatting

#### 5a. `std::precision` typo

- **Issue:** user wrote `std::precision(1)` — doesn't exist; correct is `std::setprecision(1)` from `<iomanip>`.
- **Caught immediately from code review; no conceptual issue.**

#### 5b. Sticky stream state

- **Symptom:** after first compile, parametric and MC VaR values printed as `-0.0` (then `-0.02`/`-0.03` after partial fix).
- **Root cause:** `std::fixed` and `std::setprecision` are persistent stream manipulators — they change `std::cout`'s state until explicitly reset. Historical exceedance block set them; parametric VaR values were printed with those settings still active.
- **User said "I don't know"** when asked why.
- **Explanation given:** like a calculator's "Fix 1" mode — once pressed, all subsequent numbers display 1 decimal place until you press something else. `std::fixed << std::setprecision(1)` does the same to `std::cout`. After each exceedance block, reset with `std::defaultfloat << std::setprecision(6)`. `std::defaultfloat` cancels `std::fixed`; `std::setprecision(6)` restores C++ default precision (6 significant digits).
- **Fix applied correctly ✓**
